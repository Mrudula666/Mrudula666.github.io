Case studies

Decisions, trade-offs, results
Cardinal Health · Platform90 → 35 min releases

Moving supply chain services from PCF to GKE

Problem
Onboarding and fulfilment microservices ran on PCF (Tanzu) and had to move to GKE without breaking hospital and clinic integrations.
Approach
Service-by-service cutover: buildpacks became Dockerfiles, manifests became Helm values, and service bindings moved to Secret Manager with Workload Identity. Concourse runs build, test, scan and deploy, with Cloud Build images in Artifact Registry and Python deployment checks.
Result
Average release time fell from ~90 to ~35 minutes, with health and latency visible in Cloud Monitoring.
Cardinal Health · Datap95 350 → 120 ms

One store per access pattern

Problem
Orders, pricing, audit data, archives and product search have very different access patterns, and peak pricing lookups were driving repeated database reads.
Approach
Cloud SQL for orders and pricing, BigQuery for audit and reporting, Cloud Storage for archives, Elasticsearch for search, and Memorystore cache-aside with TTL for pricing. Final order validation always reads Cloud SQL, so a stale cache can never price an order.
Result
~40% fewer pricing reads, and p95 pricing lookups fell from ~350 ms to ~120 ms at peak.
Home Depot · PaymentsPCI DSS

Capture per shipment, never charge twice

Problem
Split B2B orders ship in parts, so payment has to be captured per shipment, support partial refunds, and stay safe under retries.
Approach
A Spring Boot Payment Service on a third-party gateway with tokenized cards: authorize at checkout, capture per shipment, refund partially, guard every call with an idempotency key, publish status on RabbitMQ, and reconcile settlement from S3 with Airflow.
Result
Customers are charged per shipment on split orders, and retries never double-charge.
Home Depot · Concurrencyweekly → ~monthly

No duplicate bulk orders under retry

Problem
Concurrent bulk submissions from contractors and enterprise customers were creating duplicate orders.
Approach
Persist the idempotency key, order header and line-level reservation state in PostgreSQL before any downstream call. Camunda then orchestrates split fulfilment and exception recovery.
Result
Duplicate-order tickets dropped from a few per week to about one a month.
Cardinal Health · EventsDSCSA / EPCIS

Traceability events that are safe to redeliver

Problem
Allocated-order and serialization events feed warehouse, shipment and traceability workflows. Kafka guarantees at-least-once delivery, and consumer groups alone don't remove duplicates.
Approach
Idempotent Spring Kafka consumers keyed on a processed-event ID, with Kafka for high-volume ordered streams and Google Pub/Sub for GCP-native fan-out.
Result
Redelivered events never create duplicate fulfilment or traceability records.
TransUnion · Performance1.8 s → 450 ms

Fixing the slowest verification queries

Problem
Slow identity-verification queries on Oracle were holding up account-opening and loan verification flows.
Approach
Indexing and execution-plan tuning on Oracle behind Spring Data JPA and Hibernate, keeping profiles, verification status, OTP state and fraud records consistent.
Result
p95 on the slow queries fell from ~1.8 s to ~450 ms.
Home Depot · Production incidentrestored in ~70 min

P1: production reading a QA secret

Problem
A Helm values change made a production Kubernetes deployment read a QA AWS Secrets Manager path, and customer order-history calls began failing.
Approach
Traced the failure through pod configuration to the wrong secret path and rolled back.
Result
Service restored in ~70 minutes. A new CI check now validates secret paths per environment before every production deployment.
